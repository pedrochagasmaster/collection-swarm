Pass 1

Functional documentation

Collection Swarm is an installable Python package named collection-swarm. It exposes the collection-swarm console command, a FastAPI dashboard, a SQLite-backed results store, and an optional Node bridge for Cursor SDK model calls. The default path is offline: local scripted models let a developer run a simulation, seed demo data, and exercise most flows without credentials.

Install

pip install -e ".[dev]"

Single simulation

collection-swarm simulate \
  --profile cooperative_hardship \
  --strategy empathetic_payment_plan

Dashboard

collection-swarm seed --count 24
collection-swarm serve

Playbook

collection-swarm analyze --output output/playbook.md

Pass 2

Conceptual documentation

The project treats debt-collection strategy as a synthetic experiment rather than a direct customer workflow. A Simulation is one conversation between a Collector participant and a Debtor participant. A Run is a batch of simulations over a matrix. A Judgment is the evaluator's structured result: payment outcome, probability, satisfaction, compliance, risk, end reason, and constraint violations.

Profile Debtor archetype, account data, persona, and hard constraints.
Strategy Collector tone, tactic, escalation, concession, follow-up, and context.
Model combo Conversation model plus judge model, recorded with every result.
Playbook Regenerable analysis report that recommends safe profile-specific tactics.

Operations

Operate

Offline mode

Uses local-scripted and local-judge. This mode is for development, smoke tests, deterministic demos, and dashboard exploration.

Live model mode

NIM needs NVIDIA_NIM_API_KEY. Cursor SDK needs CURSOR_API_KEY, Node.js 22+, and installed bridge dependencies in cursor_sdk_bridge/.

Pass 4

Sequential module walkthrough

This pass walks project modules in the order a request travels through the system. Each card names the file, explains what it does functionally, and states the concept it owns.

01

Configuration layer

config.py loads YAML into a single AppConfig.

  • Functional: reads profiles, strategies, models, prompts, and simulation settings.
  • Conceptual: centralizes the experiment catalog so runtime code receives typed objects.
  • Sources: config/debtor_profiles.yaml, config/collector_strategies.yaml, config/models.yaml, config/prompts.yaml, config/simulation.yaml.
02

Domain model layer

models.py defines the project language as Pydantic models and enums.

  • Functional: validates Profile, Strategy, SimulationResult, Judgment, MatrixCell, tournament, Elo, evolution, and calibration payloads.
  • Conceptual: prevents "loose dict" drift between CLI, engine, store, and web APIs.
  • Key invariant: constraints can include structured rules, allowing deterministic verification after LLM scoring.
03

Simulation runtime

engine.py owns one complete conversation lifecycle.

  • Functional: alternates Collector and Debtor turns, strips [END_CONVERSATION], detects stalemates, applies turn limits, calls the Judge, tracks token/cost metadata, and returns a SimulationResult.
  • Conceptual: the engine is the clock. Participants only speak; they do not decide the global lifecycle.
  • Termination precedence: explicit end signal, then stalemate, then turn limit.
04

Participant and evaluator agents

agents/collector.py, agents/debtor.py, and agents/judge.py adapt domain objects into model prompts.

  • agents/collector.py: builds a strategy and account-data system prompt, then asks the router for the collector turn.
  • agents/debtor.py: injects profile persona and constraints, then translates transcript history into model messages.
  • agents/judge.py: parses JSON judgment output, normalizes common outcome aliases, and merges LLM violations with deterministic constraint checks.
  • Conceptual: Collector and Debtor are participants; Judge is the evaluator and sees the transcript plus constraints.
05

LLM backend layer

The backends/ package hides provider details behind one async completion protocol.

  • backends/base.py: declares LLMResponse and the backend protocol.
  • backends/router.py: maps model IDs to backend implementations and lazy-loads optional providers.
  • backends/scripted.py: deterministic local model for offline simulations and tests.
  • backends/nim.py: LiteLLM-backed NVIDIA NIM integration with token/cost accounting.
  • backends/cursor_sdk.py: subprocess bridge to the TypeScript Cursor SDK via cursor_sdk_bridge/run.mjs.
  • Conceptual: routing lets the experiment compare model behavior without rewriting simulation logic.
06

Persistence layer

store.py stores operational and analytical state in SQLite.

  • Functional: creates tables for runs, Elo ratings/history, tournaments, evolved strategies, evolved profiles, calibration labels, and judge prompt variants.
  • Functional: exposes save_run, list_runs, get_strategy_comparison, compliance summaries, matrix coverage, cost summaries, and pool helpers.
  • Conceptual: SQLite is the project memory. Analysis modules ask for domain-shaped answers instead of writing SQL.
07

Analysis layer

The analysis/ package turns completed simulations into recommendations.

  • analysis/statistics.py: ranks strategies for a profile by store-provided strategy stats.
  • analysis/compliance.py: excludes unsafe profile-strategy pairs below compliance or above escalation thresholds.
  • analysis/objections.py: extracts simple objection categories from debtor turns.
  • analysis/playbook.py: formats rankings, exclusions, objections, and example transcripts into Markdown.
  • Conceptual: analysis is intentionally post-hoc. Simulations produce evidence; playbooks summarize evidence.
08

Arena and evolution layer

arena.py, runner.py, evolution.py, and adversarial.py support competitive improvement loops.

  • arena.py: computes effective scores, Elo expectations, rating updates, Swiss pairings, and round-robin pairings.
  • runner.py: builds matrices, executes concurrent simulations, runs tournaments, updates Elo, and orchestrates evolution cycles.
  • evolution.py: asks an LLM to generate improved strategies as YAML, validates them, and falls back to deterministic mutation.
  • adversarial.py: hardens debtor profiles so winning strategies face harder synthetic opponents.
  • Conceptual: the system can optimize both sides of the experiment, strategies improve and profiles become more challenging.
09

Calibration and model evaluation

calibration.py and model_evaluation.py help decide whether evaluator scores and model-role choices are trustworthy.

  • calibration.py: loads human labels, compares judge scores using MAE and Pearson correlation, and reports an overall calibration score.
  • model_evaluation.py: defines role probes, runs optional Cursor SDK probes, builds reports, recommends models per role, and writes Markdown or JSON.
  • Conceptual: the project measures the measurement layer, not just the collector strategies.
10

Environment and bridge utilities

env.py and cursor_sdk_bridge/run.mjs support live-provider ergonomics.

  • env.py: loads a local .env file without overriding exported environment variables.
  • cursor_sdk_bridge/run.mjs: receives JSON over stdin, runs the Cursor TypeScript SDK, and returns JSON to Python.
  • Conceptual: credentials and provider-specific runtime constraints stay outside the core simulation loop.
11

Web dashboard layer

web/app.py, web/seed.py, and the static SPA expose Collection Swarm in the browser.

  • web/app.py: creates the FastAPI app, mounts static assets, defines dashboard, config, run, analysis, arena, evolution, calibration, benchmark, jobs, and manual-session APIs.
  • web/seed.py: generates realistic demo SimulationResult rows for local exploration.
  • web/static/index.html, web/static/styles.css, and web/static/app.js: render the dashboard SPA.
  • Conceptual: the dashboard is an operations console, not a separate domain model.
12

CLI surface

cli.py exposes every major project capability as a command.

  • Catalog: list-profiles, list-strategies.
  • Simulation: simulate, run, seed.
  • Competition: tournament, leaderboard, reset-elo, evolve.
  • Evaluation: calibrate, model-report, test-connection.
  • UX: serve launches the dashboard.
