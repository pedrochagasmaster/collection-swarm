# Collection Swarm UX Report

Date: 2026-05-02

Reviewer: Cursor Cloud agent using browser-based manual testing and independent source inspection.

Test target: `http://127.0.0.1:8000`

Test data: 24 seeded simulation runs in `output/collection_swarm.sqlite`.

## Executive Summary

Collection Swarm presents as a serious product dashboard for synthetic debt-collection strategy testing. The visual system is cohesive, the information architecture is clear, and the dashboard gives power users useful evidence about profiles, strategies, compliance, and outcomes.

The main usability problem is navigation reliability. Sidebar button activation and keyboard activation can navigate between routes, but direct hash navigation does not update page content. That breaks deep links, refresh expectations, browser-history workflows, and support handoffs.

The secondary UX issue is cognitive load. The dashboard exposes many metrics and product concepts before it gives a first-time user a confident next action. Expert users can understand the surface, but new users need stronger onboarding, clearer metric explanations, and more visible trust framing around generated playbook and judge outputs.

## Methodology

- Installed the app dependencies with `python3 -m pip install -e ".[dev]"`.
- Seeded 24 demo simulations with `collection-swarm seed --count 24`.
- Started the local FastAPI dashboard at `http://127.0.0.1:8000`.
- Verified `/api/dashboard` returned 24 completed simulations.
- Tested the dashboard in the browser across first-time and power-user flows.
- Ran an independent source-level UX and accessibility audit of the static app shell, CSS, JavaScript, and FastAPI dashboard surface.

## Browser Findings

### Pages and flows inspected

- Dashboard
- Simulation Runs
- Launch Run
- Batch Comparison
- Compliance
- Profiles
- Strategies
- Evolution
- Mobile layout around 400px width
- Keyboard navigation through the sidebar
- Direct URL hash navigation

### Runtime behavior

Sidebar and keyboard navigation can work when activating actual navigation buttons. In a verification pass, using keyboard focus plus Enter moved from Dashboard to Simulation Runs, updated the H1 to `Simulation Runs`, updated the URL hash to `#runs`, and rendered the runs table.

Direct hash navigation does not work correctly. Typing `http://127.0.0.1:8000#compliance` or `http://127.0.0.1:8000#profiles` changed the URL but left the Dashboard content and Dashboard sidebar state visible. This means deep links and browser-history workflows are unreliable.

Theme toggle behavior was not conclusively verified in the final browser pass. The source includes a plausible `toggleTheme()` implementation, so the earlier visual concern should be retested with exact element targeting before treating it as a confirmed defect.

## What Works Well

### Visual design

- Cohesive dark product UI with restrained accent use.
- Good typography choices for a technical dashboard: Inter for UI, JetBrains Mono for IDs and technical values.
- Consistent cards, badges, tables, score bars, and status states.
- Semantic color use for success, warning, danger, and info states.

### Information architecture

- Sidebar grouping is understandable: Overview, Analysis, Configuration.
- Dashboard prioritizes strategy rankings and compliance signals, which map well to the product's core decision.
- Empty states on Evolution provide clear explanations and actions.

### Accessibility foundations

- The app shell uses `nav`, `main`, and transcript `aside` semantics.
- Most icon-only controls have accessible labels.
- Focus-visible styling is present.
- Transcript slideout includes focus management and a focus trap.
- Mobile sidebar moves focus into the opened panel.
- Reduced motion is respected globally in CSS.

## Priority Issues

### P1: Direct hash and deep-link navigation do not render the target route

**What:** Manually changing the URL to `#compliance` or `#profiles` leaves Dashboard content rendered.

**Why it matters:** Users cannot reliably share links, refresh into a specific page, use browser history predictably, or hand a URL to support.

**Fix:** Add a `hashchange` listener or move routing to a single source of truth that handles click activation, initial load, `popstate`, and direct hash changes. Also update `document.title` on each route.

**Suggested command:** `$impeccable harden`

### P1: Dashboard has no clear first action

**What:** The first screen presents rankings, summaries, compliance, averages, outcomes, costs, and operational details without a dominant "what should I do next?" path.

**Why it matters:** A new analyst may understand that the tool is powerful but not know whether to launch a run, compare strategies, inspect compliance, or open a transcript first.

**Fix:** Add a first-run decision panel with 2 or 3 actions: run a demo simulation, compare strategies for one profile, review compliance risks. Keep advanced operational details collapsed by default.

**Suggested command:** `$impeccable onboard`

### P1: Generated playbook and judge reasoning need stronger trust framing

**What:** Generated guidance appears close to authoritative operational advice without enough visible sample size, freshness, uncertainty, or legal/compliance caveats in the same reading context.

**Why it matters:** This product operates in a sensitive collections domain. Users need to understand that outputs are synthetic strategy evidence, not legal advice or direct consumer policy.

**Fix:** Add persistent trust metadata near generated content: source run count, date generated, model pair, compliance threshold, limitations, and a brief "review before operational use" note.

**Suggested command:** `$impeccable clarify`

### P2: Some accessibility semantics are incomplete

**What:** Source inspection found several specific gaps: no skip link, `aria-live="polite"` on the whole main content area, mobile menu missing `aria-expanded`, sortable columns missing `aria-sort`, and benchmark tabs lacking the full keyboard/tab pattern.

**Why it matters:** The app is already close to a strong accessibility baseline. These gaps mainly affect screen-reader verbosity, keyboard efficiency, and predictable interaction patterns.

**Fix:** Add a skip link, narrow live regions to status-only content, maintain `aria-expanded` on the mobile menu button, set `aria-sort` on sortable table headers, and align benchmark tabs with the dashboard tab behavior.

**Suggested command:** `$impeccable audit`

### P2: Runs table rows are not fully keyboard equivalent

**What:** Rows use click-to-open behavior, while keyboard users rely on the smaller "View" button. A keyboard helper exists in source but is not wired to row markup.

**Why it matters:** Power users reviewing many transcripts need fast keyboard access to row details.

**Fix:** Either wire row keyboard handlers with correct role semantics or keep rows passive and make the primary row action more prominent and consistently reachable.

**Suggested command:** `$impeccable harden`

### P2: Mobile behavior needs task-level validation

**What:** At roughly 400px width, the hamburger button appears and responsive rules are present. Dense tables, charts, filters, and side panels still need full task validation.

**Why it matters:** The app is likely desktop-first, but users may still triage results on smaller screens. Dense data surfaces can become unusable if horizontal scrolling, touch targets, or overlays are not tuned.

**Fix:** Test the core tasks at 390px, 768px, and 1024px: open runs, filter runs, open transcript, launch a run, inspect compliance, and navigate back.

**Suggested command:** `$impeccable adapt`

## Persona Red Flags

### First-time analyst

- The dashboard confirms the product is powerful but does not clearly answer "start here."
- Metric names like Success, Payment Probability, Rapport, and Escalation Risk need visible explanations, not only hidden hover text.
- Profile and strategy IDs are meaningful to maintainers but harder for newcomers to scan.

### Operations power user

- Deep links failing makes support, bookmarks, saved workflows, and browser history unreliable.
- Row-level transcript review can be faster with better keyboard affordances.
- Filters and sort states should be shareable in the URL for repeat analysis workflows.

### Compliance reviewer

- Compliance warnings are prominent, which is good.
- Generated recommendations and judge reasoning need stronger caveats, evidence counts, and review status.
- The product should clearly distinguish simulation evidence from approved operational policy.

## Minor Observations

- `document.title` remains generic across pages, reducing browser-tab wayfinding.
- Route params are kept in `history.state`, but not encoded in the URL, so reloads lose selected profile/demo context.
- Metric help via `title` is easy to miss and inconsistent for keyboard and assistive tech users.
- Heatmap and chart elements should expose text summaries for screen readers.
- Small uppercase labels may become hard to read on mobile or lower-quality displays.

## Recommended Action Plan

1. **P1 `$impeccable harden`**: Fix hash/deep-link routing, browser history behavior, document titles, and route-param persistence.
2. **P1 `$impeccable onboard`**: Add a guided first-run dashboard path and reduce first-screen cognitive load.
3. **P1 `$impeccable clarify`**: Add trust framing to generated playbook, judge reasoning, compliance output, and metric labels.
4. **P2 `$impeccable audit`**: Complete accessibility fixes for skip links, live regions, menu state, sortable tables, and tabs.
5. **P2 `$impeccable adapt`**: Validate and tune dense workflows on mobile and tablet breakpoints.
6. **Final `$impeccable polish`**: Re-run browser testing and confirm the UX score improves.
