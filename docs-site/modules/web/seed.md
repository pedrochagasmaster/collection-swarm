# `web/seed.py` — demo data generator

<span class="cs-kicker">collection_swarm/web/seed.py</span>

A 190-line module with a single public function — `generate_seed_data()`
— that inserts realistic demo runs into the SQLite store. The CLI
`seed` command is a thin wrapper.

<dl class="cs-summary">
  <dt>Imports</dt><dd><code>random</code>, datetime, domain models, the store</dd>
  <dt>Side effects</dt><dd>Writes rows to the configured SQLite database</dd>
  <dt>Determinism</dt><dd>Transcripts are deterministic; metric jitter is random</dd>
</dl>

## Why it exists

A fresh dashboard with an empty database is useless for evaluating UX,
explaining the system, or onboarding contributors. Seed data closes
that gap without requiring API keys.

## Constants

`SEED_COMBOS` — ten canonical (Profile, Strategy) pairs that span the
shipped catalog. Each is the "right" Strategy for that Profile. Examples:

- `("cooperative_hardship", "empathetic_payment_plan")`
- `("hostile_avoidant", "neutral_reminder")`
- `("liquidation_confused", "liquidation_explainer")`
- `("willbank_low_digital_access", "low_digital_access_guidance")`

`SAMPLE_CONVERSATIONS` — hand-written transcripts for the most
illustrative pairs. Includes both English and Brazilian-Portuguese
flavors so the dashboard's run list shows variety.

`OUTCOMES_BY_COMBO` — the baseline Judgment vector for each pair:

```python
("cooperative_hardship", "empathetic_payment_plan"):
    ("payment_plan", 0.82, 0.88, 0.95, 0.85, 0.08, "agreement_reached"),
```

The tuple is `(payment_outcome, payment_probability, debtor_satisfaction,
compliance_score, rapport_built, escalation_risk, end_reason)`.

## `generate_seed_data(db_path, num_runs)`

Loops `num_runs` times, picks a `(profile_id, strategy_id)` from
`SEED_COMBOS` round-robin, and:

1. Builds a transcript: hand-written if `(profile_id, strategy_id)` is in
   `SAMPLE_CONVERSATIONS`, otherwise generated by
   `_generate_generic_transcript()`.
2. Picks a baseline metric vector from `OUTCOMES_BY_COMBO`, defaulting
   to a no-commitment baseline if unmatched.
3. Jitters every score by `±0.08` and clamps to `[0, 1]` so two runs
   with the same seed combo don't produce identical Judgments.
4. Builds a `Judgment` with the jittered scores. Optionally injects an
   `excessive_pressure` Constraint Violation when escalation risk is
   high (40% probability when `er > 0.5`).
5. Builds a `SimulationResult` stamped with synthetic timestamps,
   transcript, judgment, and randomised token / cost counts.
6. Bulk-saves the list with `store.save_runs(results)`.

## CLI wrapping

```python
@cli.command("seed")
@click.option("--count", default=24, ...)
@click.pass_context
def seed_data(ctx, count):
    n = generate_seed_data(db_path=ctx.obj["db_path"], num_runs=count)
    console.print(f"Seeded {n} simulations into {ctx.obj['db_path']}")
```

A second invocation appends another batch — the seed runs are not
idempotent, but they are isolated from real runs because their
`conversation_model="scripted_echo"` and `judge_model="heuristic_judge"`
identifiers are namespaced.

## When to re-seed

- Before recording a demo of the dashboard.
- When onboarding someone who hasn't run anything yet.
- After wiping the database (`rm output/collection_swarm.sqlite`).

For real evaluation, never seed — you want every run in the database to
be a real one.
